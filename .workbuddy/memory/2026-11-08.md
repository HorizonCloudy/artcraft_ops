### 线上修的两个用户可见缺陷（均已真机验证）

#### 1. VectorCraft 步数计数虚高（`result.py`）
- 现象：只下 1 个 `--cmd`，用户看到「共 3 步」。VectorCraft 的 stdout 是 **3 行协议转录**：
  `step=open`（无 command）/ `step=cmd`（有 command）/ `step=export`（无 command），
  原实现把所有可解析 JSON 行都算步 → 3。
- 不是 VC 特例：PhotoCraft 5 行全带 `command`（巧合正确）；Craft Anything 单行只有 `result`（0 个 command）。
- 修法：新增模块级纯函数 **`command_step_count(steps)`** —— 数带 `command` 的条目，
  为 0 时回退 `len(items)`（覆盖 CA 形状），容忍 `None`/非 dict。
  只切**计数口径**，`ExecResult.steps` 与 `_spill()` 的完整转录保持不动。
- 切点：`result.py:162`（en 文案）/ `:164`（zh 文案）/ `:237`（`materialize` 的 `step_count`），
  `__all__` 补名。真机结果：VC `协议转录 3 / 命令步数 1 / 用户文案「共 1 步」`。

#### 2. spill 回执写「共 0 步」（`result.py:288-296`）
- 现象：回包 >512 KiB 触发落盘时，spill 分支临时 `ExecResult` 没带 `steps`，
  摘要写成「共 0 步」。
- 修法：补 `exit_code=r.exit_code` + `steps=r.steps`（计数必须基于完整 steps，不截断）。
- 实测（`max_bytes=512` 逼出 spill，PhotoCraft 5 步）：`summary=任务完成：photocraft；共 5 步`，
  落盘 JSON 仍保留 5 条转录。

#### 附带诊断（`runner.py:194-200`）
`stderr` 排空 `wait_for(timeout=0.5)` 超时分支加 `logger.warning(...; stderr may be partial)`——
`stderr_text` 是 `CLI_USAGE_ERROR`/`CLI_TASK_FAILED` 的文案来源，静默截半会误导根因。纯日志、零行为变更。

**最强版（推荐，零噪音、无名字过滤、无 maxdepth）——环境隔离审计**
给 pytest **子进程**把 `TEMP`/`TMP`/`TMPDIR` 指到一个空目录，跑完断言该目录为空。
噪音由构造消除（harness 用它自己启动时的 TEMP，不受子进程 env 影响），
既不会误报也不会假绿，且与泄漏文件叫什么名字无关：
```python
base = os.path.join(tempfile.gettempdir(), "artcraft_iso_tmp"); os.makedirs(base, exist_ok=True)
env = dict(os.environ, TEMP=base, TMP=base, TMPDIR=base)
subprocess.run([sys.executable, "-m", "pytest", "artcraft_ops/tests", "-q", "--no-header"], env=env)
assert os.listdir(base) == []          # 实测：exit 0 / 138 passed / 0 残留条目
shutil.rmtree(base, ignore_errors=True)
```
注意 `tempfile.gettempdir()` 在子进程里读 `TEMP` → 一切"默认落点"泄漏（spill、
conftest 的 `_TMP_BASE`）都会落进隔离目录，等于**全形态覆盖**。

**扫描法的固有缺陷（实测踩到）**：它会抓到审计者自己的产物（我把 pytest 输出重定向到
`/tmp/_p.html`，那正是 `%TEMP%`，立刻被算成命中）。scan 口径必须排除：自己这次的输出文件、
`codebuddy-*`、`cv_debug.log`、`save-on-subagent-stop.log`、UUID `.tmp`。
